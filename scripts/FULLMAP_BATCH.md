## 执行器分类

| 阶段 | 脚本 | 验收内容 |
|---|---|---|
| 设施 | `fullmap_batch.py`、`fullmap_facility.lua` | 当前姿态、归属、货运终端、仓储容量、维护参数 |
| 接路 | `fullmap_roads.py`、`fullmap_road_audit.lua` | 实际端口与锚点、CAR/TRUCK双向直接转弯 |
| 路口修补 | `fullmap_junction_patch.lua` | 限2或3条原道路、1条新增支路、4车道；保留原转向、全部横道、信号配置 |
| 卸货点 | `fullmap_stops.py`、`fullmap_stop_audit.lua` | 当前build_street_stop、按道路两端坐标重解析、终端网络与货运卸货 |
| 中转覆盖 | `fullmap_hub_audit.py` | 货站/直升机坪/码头对同一仓库实体和库存的实际catchables |
| 城市覆盖 | `fullmap_city_coverage.py` | 全城有需求库存点的实际卸货覆盖，不以半径估算替代 |
| 线路 | `fullmap_lines.py`、`fullmap_lines.lua` | 原生闭合寻路选择站台；来源装目标货物、目的地不装货；完整cargoId+1向量 |
| 首批车辆 | `fullmap_vehicles.py`、`fullmap_vehicles.lua` | 每条已验收线路最多1辆；购置设施兼容、分配；实际驶离基地、正常运行和原生故障结果；船舶限定本港计划船坞 |
| 运行观察 | `fullmap_observe.py`、`fullmap_observe.lua` | 有限时运行，采集装货、城市收货和寻路状态，结束暂停并原生存档 |

## 运行规则

全部游戏脚本共享互斥锁和同一日志，禁止并发操作游戏。每次施工先重新确认原16城18产业及日志中已核对的自动新增产业会话指纹，按坐标/资源解析当前对象，再预览、单次提交、独立读回。当前批次道路、停靠点和线路不得按旧实体编号重新执行。

日志写入 `commit_started` 后才提交。未知结果、超时或部分成功锁定后续写操作，先查询现场。只有在明确拒绝且现场实体、运输网络组件及拓扑均完成核对后，才可记录对账结论；原生断言后停止整批修改，不能凭现场无新增实体继续独立作业。原操作仍不重发。新选址使用独立修订操作编号，保留旧证据。

船坞原生预览必须检查 `errorState.infos`、`messages`、`warnings`，不能只看 `critical`。本机实测“放置在海岸线上”位于 infos 且 critical=false；旧脚本漏读该字段才导致预览误判。已修正共用 previewProposal 和本批设施执行器。第二座船坞以75°朝向的新修订通过完整字段、碰撞、水域采样后单次建成，第三座也已建成，两条水运线均已购船。旧失败日志保留，未重发、未使用 ignoreErrors。网上当前文档中的 Proposal 参数与本机 SimpleProposal 类型不一致，不能直接套用。

已建3座船坞具备原生维护池与覆盖半径；实际维护周期仍需运行验证。水面实体单独记录，不与建筑/道路碰撞混为一谈。

道路粗采样走廊需要替换为实际建筑入口，删除越过入口平面的回头控制点。港区第二条接路避让已建维护设施；以无碰撞原生预览和双向路径验收为准。新接路不删除既有道路。

52个计划卸货点实际建51组双向站点；`STOP49838_02` 与01同道路，01的原生覆盖已经包含02全部目标建筑，日志记录别名复用，线路去重。全图16城需求库存覆盖验收报告在 `execution/city_coverage.json`；城市增长后需重新核验。

## 执行速度优化（2026-10-03）

最新入口见[集合检查与批量读取](../docs/guides/GROUPED_CONSTRUCTION_WORKFLOW.md)：设施会话与读取合并为单请求、道路聚合验收、共享枢纽集合清单。下文“两次请求/批”的设施说明是此前实现；新 CLI 默认启用合并读取。集合清单仍需联合原生验证，不自动批准施工。

### 新增：规划前置检查与统一交付

新地图初稿先运行 `fullmap_workflow.py`，见[统一规划准备流程](../docs/guides/PLANNING_WORKFLOW.md)。它把唯一编号、跨文件引用、任务覆盖与清单一致性、旋转占地、道路候选、依赖增量、分类报告和计时合为一次离线调用。设施执行器同步增加重复编号拦截，避免预览后才发现结果覆盖。新增设施编号按 owner/context/role 区分岸边和航空枢纽，不静默修补历史引用。

选址工具支持显式 `access` 锚点和局部入口，在候选排序前做同岸/坡度粗筛。缓存仅存同快照的离线道路筛选；几何复核不跳过，原生预览不缓存。缺尺寸、旧清单缺产业指纹及接路未解决均显式报告。约0.8秒离线回放不代表完整规划或施工耗时。

### 完整准备流程：道路筛选、批次顺序与计时报告

`fullmap_prepare.py` 是离线准备入口，不连接游戏、不修改方案或存档。输入当前方案、对应地图快照和执行清单，核对城市/产业名称资源及位置、玩家，再输出道路候选和依赖顺序。输出记录三个输入文件的 SHA-256；仍不得用摘要代替当前游戏会话核验。

- 一次准备运行共用地形插值缓存和空间障碍索引；采样缓存最多10万项，重新运行重新建立，没有跨重载或跨施工复用实体的持久缓存。
- 每条道路比较直线、已有走廊及有限平滑绕行候选；先本地剔除超出快照、水域、明显障碍、陡坡和超预算路径，再按距离与爬升排序，最多保留3项待原生预览。没有候选就标为需要局部重新设计，不无限搜索。默认10%地形坡度只是筛选偏好，不是游戏原生坡度上限。
- 路端20米内的障碍不用于粗筛否决，必须独立验证实际端口、接入方向、建筑碰撞和坡度；现有道路交叉也需要另行原生设计。该工具不证明接路可建，不生成可直接提交的历史实体ID参数。
- 执行顺序按已满足的依赖优先选择附近项目，每8项形成建议批次，未知依赖、重复ID及循环依赖会报错。批次文件是调度建议，不自动调用施工，不授予线路、车辆或模拟运行权限。
- 原生预览阶段以候选上限为预算；明确几何拒绝可换下一个候选，断言、超时或未知结果必须停止，不能耗完预算继续试。每次正式提交前仍重新解析和预览。

```powershell
# 所有路径均须指向同一地图的输入；此命令完全离线。
server/.venv/Scripts/python.exe scripts/fullmap_prepare.py --plan <方案.json> --snapshot <快照.json> --manifest <执行清单.json> --output <准备结果.json>
# 查看已执行任务的实测分阶段数据；baseline必须是同等工作量才有比较意义。
server/.venv/Scripts/python.exe scripts/fullmap_performance.py <ledger.json> --baseline <旧ledger.json> --output <耗时报告.json>
```

### 新增：设施只读分批与请求内索引

`fullmap_batch.py preview/verify` 默认 `--read-batch-size 8`（1至16；设为1回到逐项读取）。三门峡入口 `construct.py facilities preview/verify` 同样支持。每批一次完整会话检查、一次设施读取，不跨引擎请求缓存实体或组件。144处设施由约289次请求降为36次，不含外部调查；这是请求数量估算，不是游戏耗时实测。

`fullmap_facility_index.lua` 在同一只读请求内扫描一次建筑和仓储组件，按资源及仓库所属建筑整理索引。批内各设施复用索引，下一请求重新生成；不向全局写入，不向 build 注入。原生预览和审计仍逐设施执行。已知预览不通过会保留原因并继续只读筛选；Lua请求错误、超时、已建项目审计失败或历史提交消失会停止后续批次，不自动重试。

实际建造继续逐项会话检查、重新预览、单次提交和独立读回，存档频率未降低。设施只读批处理与上述道路离线筛选分别生效；没有跨会话的通用地形缓存，也不合并世界修改。

执行账本增加 `performance`，记录桥接请求、会话检查、设施 preview/build/verify、只读批次及保存的调用次数、累计秒数、最大秒数和失败数。计时按执行器生命周期累计并随账本写入，嵌套阶段时间不能相加作为总耗时。崩溃前未落盘的最后一项计时可能缺失；计时字段不是提交成功凭据。下一次经授权运行可据此识别真实瓶颈，本轮没有连接游戏做计时对比。

验证覆盖8项分批、限额、重复建筑、请求内索引复用及下次请求失效、缺失历史提交中止、超时不重试、禁止批量build；原有单次提交、保存覆盖和失败中止测试保留。

### 既有：逐项施工的请求合并

设施执行器将“是否已建的查询”和“未建设施的预览”合为一次调用：Lua 先按当前坐标/资源重新解析，已有设施直接审计，未建才预览。会话检查将游戏状态和地图信息合并为同一次引擎读取，每项仍重新查询，不缓存跨施工实体编号。

每个未建设施的常规桥接请求从6次减至4次（会话2→1、查重与预览2→1、提交1、独立验收1）；不计批次启动与存档。提交调用内部仍重新预览并单次提交。道路、停靠点、线路和购车执行器继承合并后的会话读取，设施查重优化仅适用于 `fullmap_batch.py`。

仍保留互斥锁、逐项提交前日志、每10项检查点存档、施工前后存档，以及超时/部分成功后的停止对账；不并发写游戏。离线测试覆盖调用次数、断点续跑不重复建造、预览拒绝、超时、独立验收失败及会话变化。当前桥接心跳过期，未完成游戏内耗时对比；减少请求次数不等同于已实测同比提速。

## 常用命令

批量自动存档使用固定槽 `tf3_fullmap_auto_<planDigest前16位>`，检查点、各施工阶段结束及运行观察结束覆盖该槽；不同输出目录只要属于同一规划便共用该槽。施工前备份和异常现场仍独立命名保留。覆盖验收比较保存前后文件状态并等待写入稳定，避免误将旧文件判为新保存成功；历史存档不自动删除。此规则适用于使用 `Batch.save` 的执行器，不修改游戏内置定时自动存档设置。

```powershell
server/.venv/Scripts/python.exe scripts/fullmap_batch.py verify --ids HQ,DEPOT49835
server/.venv/Scripts/python.exe scripts/fullmap_hub_audit.py
server/.venv/Scripts/python.exe scripts/fullmap_city_coverage.py
server/.venv/Scripts/python.exe scripts/fullmap_lines.py preview --line-ids R001
server/.venv/Scripts/python.exe scripts/fullmap_vehicles.py preview --line-ids R001
server/.venv/Scripts/python.exe scripts/fullmap_observe.py --seconds 120 --speed 4
server/.venv/Scripts/python.exe -m unittest discover -s scripts/tests -p test_fullmap_batch.py
```

只读动作使用preview/verify；`build`会实际改变游戏，必须在授权范围和未解决提交协调完毕后使用。观察脚本会推进模拟，保留独立的观察前备份，结束后更新固定自动存档。原生保存使用空回调，并确认sav文件本次更新且写入稳定，不使用Computer Use。

`static_verified`、车辆`noPath=false`与短时运行未复现断言，都不等于长期稳定。线路闭合、实际装货、城市收货、全量产能和长期维护分别验收。当前产地总产能仍受原规划供需上限约束，首批1辆不是满需求运力配置。
