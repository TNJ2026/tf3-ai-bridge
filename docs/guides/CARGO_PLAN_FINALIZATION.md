# 货运规划收尾与执行契约

本指南是维护分流、全链时效、平台负荷和交付一致性的统一入口。具体机制分别引用[总部建设](HQ_ACCESS_DIAGNOSTIC.md)、[主仓库共库检查](../strategy/TRANSPORT_CARGO_CONNECTIONS.md#主仓库共库检查)、[船舶故障诊断](SHIP_ROUTE_CHECKS.md)。时效和占用均为规划参考，不是常规投运门槛；完整往返诊断仅显式要求时执行。

2026-10-12 范围更正：普通单线或小型供给链按[按需调查流程](ROUTE_PLANNING.md)交付路线说明，无需生成完整执行包或运行本指南的收尾脚本。下列流程用于已有完整执行包；默认运营分析为 `basic`，仅保留维护候选和终端分配。仅专项优化时使用 `plan_finalize.py --pack <目录> --operations-analysis detailed` 启用下面的时效、班次与占用计算；用 `--operations-analysis basic` 切回。未知数据不触发补采或容量复核，原有输入预测不作为基础模式的新分析结果。

## 离线收尾

初稿使用 `scripts/plan_pipeline.py`。选址及线路精修完成后，运行：

```powershell
server/.venv/Scripts/python.exe scripts/plan_finalize.py --pack <规划目录>
server/.venv/Scripts/python.exe scripts/plan_finalize.py --pack <规划目录> --check
```

收尾不连接游戏、不改变设施位置、不添加线路或车辆，也不恢复监控。首次保留 `before_operations_update/`；保留已提交意图和历史回执，不以历史对账阻止离线更新，也不因新摘要而重放旧操作。

`network_plan.json` 是计划源。收尾同步执行任务、逐线购车清单、完整联合规格、船舶航段、报告输入与说明；`delivery_integrity.json` 绑定当前计划和派生文件摘要。`--check` 为只读，检查摘要、设施坐标和朝向、线路任务、车辆清单及道路消费归属。任何变更后重新生成并检查，不能混用不同修订的 CSV、图表和执行清单。历史渲染图不自动变成当前图；只在最终展示阶段按规划工具流程导出一次卡片。

## 运营预测

### 航空维护

优先评估线路两端具备维护能力的直升机场，按预计机队数量分配。明确不具备维护能力的设施排除；能力未知者只能作为待验候选。两端无候选时，先比较经基地绕行的额外距离，仅在最小绕行额外 500 米以内的候选中比较负荷；500 米是排序余量，不是维护覆盖半径或安全距离。

维护基地与采购基地独立。维护需求不计入当地装卸吞吐。计划字段不自动设置游戏中的维护行为，执行前还需核实实际维护能力、合理接入、负荷估算与游戏配置；不额外验证返航。

### 全程交付时效

沿每个货流的运输链累计单程行程和等待；等待初筛取该段半个发车间隔。同段并行线路按货量加权，不能将两条平行航空线串联相加。使用细化线路的实际起终点；额外停机坪仅在明确归属同一主仓库的规划关系下归入同段，真实共库仍须另验。

期限优先读取货物本身配置；缺失时取相关线路的最严格期限并标注保守估算。缺少班次或运输段数据时将预测标为未知，不阻止投运。该预测不是游戏实际超时结论；仅在明确的时效优化或故障诊断任务中核验计时与排队，不为常规验收增加采样。海上资源不能直接以陆路估计替代船舶集货。

### 平台负荷

每个平台最多三条线；基础模式仅记录已知终端分配，未知终端留待执行前绑定。专项分析才按实际规划终端汇总到达频率，以每次停坪 60 秒估算占用，达到 70% 时提示容量复核；这两个值是初筛假设，不是已验证的游戏容量。未知班次或占用不触发复核。维护占用与真实排队尚未计入，低于阈值也不构成运营通过。扩建、分流或转汽车运输须比较整条供给链，不为低运量单独取消时效有优势的航线。

## 按阶段执行

| 阶段 | 所需证据 | 公共入口 |
| --- | --- | --- |
| 建前 | 授权范围、当前会话、备份、重新解析节点、当前联合原生预览 | `build_joint_collection.py preview` |
| 单组施工 | 预览与提交采用同一规格、持久化意图、只提交一次 | `build_joint_collection.py build`；多组使用 `construct_planned_map.py` |
| 每组建后 | 实体和模块、道路及实际连接、机场实际接路、主仓库库存、维护、角色所需换乘 | 集合执行器独立读回；捕鱼共库独立检查，不自动调用船舶往返诊断 |
| 线路和购车前 | 基础设施已验、货品配置和终端、车型可用与货舱兼容、指定采购基地兼容 | `fullmap_lines.py`、`fullmap_fleet.py` |
| 运营 | 实际驶离基地、正常执行线路、无原生线路故障；不额外往返或数量验收 | 按用户授权验证；不自动恢复暂停的监控 |

联合入口包含设施、组内道路和外接道路；外接道路锚点按当前位置重新解析，旧编号仅是规划提示。`--compiled-dir` 要求摘要及编译内容匹配当前计划。消费过的道路写入账本，不再通过独立道路入口提交。不能用旧专用预览脚本再次追加外接道路。

购车统一使用 `fullmap_fleet.py --fleet <fleet_manifest.json>`：每线车型、数量及指定采购基地必须一致，每辆独立记录意图和读回；未知结果或部分成功停批，不重发。旧 `fullmap_vehicles.py` 的单车启动模式不接收现代 `line_specs` 计划。

建后证据在施工前标记待验；不能要求这些证据事先存在而陷入循环，也不能提前标通过。`constructionReady` 仍是整包汇总，不代替每个阶段的具体门槛。只规划不改变游戏；代码测试通过不等于新增执行路径已完成原生验收。

## 供给边界

同时报告服务对象覆盖、逐城市需求缺口和资源类型缺失。地图上存在某资源但产能不足时，只记录扩产和分期运力，不据此自动勘探。无限资金仅排除成本比较，其余通达、吞吐、噪声、污染、增长及扩建因素仍须考虑。
