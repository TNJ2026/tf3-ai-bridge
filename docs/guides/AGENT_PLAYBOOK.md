## 1. 任务范围与执行约定

定时监控的逐轮检查、人口150公交门槛、新需求与需求变更后的供给复查、载具维护、仓库扩容／上游减车、去重账本和通知规则统一见[每轮监控清单](MONITORING_WORKFLOW.md)。2026-10-05 用户已要求暂停监控；文档或模板更新不自动恢复任务，恢复须有用户明确要求。

1. 确定任务是只读调查、只规划、建造基础设施、创建线路还是购车。不要把创建线路扩大成擅自购车，也不要把只规划扩大成施工。
2. 用户已授权的正常操作直接推进，不反复要求确认。仅在缺少必要目标、需要重载存档或检测到同时手动施工等真实阻碍时询问。
3. 规划阶段不暂停游戏。需要一致性快照、批量替换停靠点或受控复现时，说明暂停目的，遵循已获授权范围；记录原速度，完成后恢复。若正在诊断故障，不自动恢复到高速模拟。
4. 不同类别的改动分阶段完成：道路 → 站点 → 无车辆线路 → 少量车辆。每阶段保存结果，避免出错后无法分辨是哪项改动导致。
5. 预览、提交和验证之间保持目标一致。人工改路即使在暂停时也会改变实体；检测到变化就重新调查，不能与用户同时替换同一路段。

## 3. 地图采集与快速规划

全局与局部布局优先使用 `capture_planning_snapshot` → `plan_global_development` / `plan_local_development`，规划过程中只保存方案 JSON、返回数据，不显示中间卡片。全部规划完成后调用一次 `export_planning_report` 导出 HTML、PNG、SVG、JSON 并显示最终结果卡片；用户要求重新显示时也使用该工具，不自动打开 HTML。参数和边界见 [规划工具说明](../reference/PLANNING_TOOLS.md)。全局联系线与局部地表走廊不能直接用于施工；进入工程设计时继续使用下述流程。

交通建筑分类选址建议见[交通设施选址指南](../strategy/TRANSPORT_FACILITY_SITING.md)，覆盖铁路、公路、港口、航空、仓储中转与维护。按官方机制、本地验证和规划建议的边界使用。

规划交通建筑时，按[配套矩阵](../strategy/TRANSPORT_CARGO_CONNECTIONS.md#各类建筑配套矩阵)列出仓库、各运输段终端及客运接驳的缺失项。按直取、直送、中转、纯客运、购置维护分别判断；不按建筑名称一律加仓库，不把维护范围当货物覆盖。

### 3.1 先用缓存和局部走廊

停靠点、仓库和车站等陆地设施需要选址时，优先“单次局部调查 → `find_facility_sites` 批量本地筛选 → 少量候选实时核对／预览”，不要逐点反复请求游戏。同一快照可用于多个需求与条件比较；选定布局后用 `plan_local_development` 校验相互冲突和接驳。快照过期、道路改变或换档时重新调查。参数与性能边界见[批量选址说明](../reference/SITE_SELECTION.md)。

按以下顺序规划，不逐点反复向游戏请求：

1. 读取起终点、建筑包围盒、城镇归属、既有道路/铁路、地形和设施端口。
2. 先构造两点直线，检查穿过的建成区和单栋建筑。
3. 绕开整体城镇范围及单独建筑；起终点位于城镇内时允许进出建成区，但仍避开建筑。
4. 对候选走廊检查地形坡度、水域、既有道路、桥隧可能性和端口朝向。
5. 生成平缓曲线，比较长度、土方、桥隧及接入难度，再做原生预览。

现有 `plan_rail_connection` 实现了分阶段铁路规划；不能声称它就是通用道路规划接口。道路应使用已存在且经审查的道路实现，不能把铁路参数直接套用。

`map_cache_control` 支持 `start/status/refresh/invalidate/stop`。缓存默认每 15 秒轮询、每五分钟全量对账，**不是逐帧同步**。手动改动有检测延迟；换档必须失效缓存；施工前刷新，施工后重新解析目标。离线快照只用于重放和比较，不能直接授权当前地图施工。

### 3.2 完整性边界

- 分页读取实体要持续到 `hasMore=false`，使用同一 ID 快照并在完成后释放。ID 快照不是所有组件同一帧的原子快照。
- `opaque_userdata`、`_unavailableFields`、`_truncated` 表示未能完整读取，不表示空值或无障碍。优先按官方类型定义读取具体字段。
- 地形粗采样不能证明微地形可施工；数据图不等于渲染纹理像素；基础地形不一定包含当前设施地表对齐。
- 车库可能以模型呈现，不能只检查 `CONSTRUCTION` 和 `TOWN_BUILDING` 而漏掉模型障碍。
- 候选 `buildable=null` 或升级预览的 `validation="structural_only"` 不是通过原生施工校验。

### 3.3 设施升级空间预留

规划设施选址及周边建设时，应考虑设施升级、增设模块后的占用面积，尽量保留连续、可接入的扩建空间。按合理的后续扩建目标预留，不仅检查当前建筑能否放下。

- 优先根据原生模块槽位、模块尺寸和升级方案判断扩建方向与范围；同时考虑站台或股道加长、仓储扩容、泊位增设等需求。暂时无法取得准确尺寸时，注明估算依据和待核对范围，不把预留区域宣称为已通过施工校验。
- 将升级后的建筑占地、出入口及必要的道路/铁路接驳通道一并纳入布局。港口还需保留岸线和船舶进出水域；避免新增道路、铁路或其他设施占据主要扩建方向，导致升级必须大规模拆迁或断开运输线路。
- 在方案中标注当前占地、建议预留区域、可扩建方向及受限边界。比较候选位置时，将升级余量与当前造价、运输距离和地形条件一起考虑。
- 地形、岸线或既有建设使预留不足时，明确说明可扩建的范围、升级可能涉及的迁改，以及可行替代位置。预留空间本身不授权提前升级、拆除或搬迁。

### 3.4 总部与公路车库的固定选址规则

2026-10-02 用户指定默认选址，以减少反复比较候选点的耗时。后续新规划优先按以下规则执行；这是用户布局偏好，不是官方强制选址要求。

- **总部**：在主城中间道路末端附近的道路侧边，按距城中心由近到远筛选首个可行位置；入口面向道路，核对旋转占地、入口高差、自动连接和扩建空间。详细参数及施工流程统一见[总部建设指南](HQ_ACCESS_DIAGNOSTIC.md)。
- **公路车库**：选在城市道路与外部道路连接口的路边，优先连接口外侧、紧邻既有道路的可用地。多个连接口时优先服务当前目标线路的出口；尚无目标线路时按距城镇中心由近到远检查。入口朝向道路，保留出入通道和扩建方向。
- **快速执行**：一份局部快照内按上述顺序筛选，首个满足条件的位置即作为默认方案，不再进行全城评分或多轮位置优化。固定的是选址规则，不能复用历史坐标、实体编号或预览。施工仍须重新确认会话、检查真实道路接入、地形、碰撞及升级空间，原生预览通过后单次提交并读回。
- 首选位置不满足条件时，先在同一道路末端或同一连接口附近调整位置、朝向或路侧，再检查下一处同类位置。空间不足时说明升级限制；没有符合规则的可行位置时说明具体障碍，不擅自拆迁或改用远处空地。
- 本规则用于后续选址，不自动搬迁或重建已建好的总部、车库；维修设施仍按线路覆盖和容量另行规划。

选址比较时读取建造预览 `check.reputation`：只有 `available=true` 才可引用扣分；单位为百分点，并按 `towns` 查看受影响城市及原因。`available=false` 不是零影响。该值是原生施工界面预估口径，不代表扣除既有历史后的最终声誉，也不包括运营噪声和污染。

## 4. 每次写操作的闭环

### 全图批量执行与恢复原则

全图准备可先用 `scripts/fullmap_prepare.py` 对同图快照进行本地道路粗筛及依赖调度，最多保留3个原生预览候选；无候选则转局部设计，不无限试路。它仅输出建议，不能绕过端口、原生碰撞、声誉、升级空间和当前会话验证。设施及卸货点只读验收默认8项一批，建造仍逐项执行。实测阶段耗时通过 `scripts/fullmap_performance.py` 读取账本，不能用本地筛选耗时代表游戏总耗时。

设施只读预览/验收可使用 `fullmap_batch.py --read-batch-size 8`，每批一次会话检查和一次请求内索引扫描；实际建造仍逐项检查与提交。性能计时写入账本 `performance`，详见[批量执行速度说明](../../scripts/FULLMAP_BATCH.md#执行速度优化2026-10-03)。不得把请求数量下降当作游戏实测耗时下降。

2026-10-03 [三门峡全图复盘](SANMENXIA_PLANNING_REVIEW_20261003.md)：设施与接入道路联合选址，长接路先核对走廊；执行按代表性供给链小批推进，不先铺完全部建筑再集中验证道路。线路、购车和运营观察仍各自受用户授权约束。

原生断言、未知结果、部分成功或超时发生后，停止整批世界修改，先只读核对组件与拓扑；其他区域看似正常不构成继续施工的依据。重载后保留历史请求记录，另建当前会话验收状态，重新解析实体并区分保留、回档及待核对项目。无原生道路端口的项目须注明实际接入机制或待验证状态，不能直接计为功能验收通过。

批量提速通过合并只读调查、本地候选筛选和同会话快照复用实现，不省略提交后检查。独立施工前基线、滚动自动存档、异常现场分别管理；记录完整文件名、时间、大小和验收阶段，避免误选带 autosave_ 前缀的同名后续存档。

| 阶段 | 必须留下的证据 | 不满足时 |
|---|---|---|
| 调查 | 会话时间、目标类型/位置、当前 ID、端口/道路引用、已有线路车辆 | 重新定位，不凭旧 ID 猜 |
| 备份 | 独立命名的施工前存档；重要改造保留稳定基线 | 保存结果不明确时先核对 |
| 预览 | 当前输入、几何/拓扑检查、碰撞和错误；注明预览能力边界 | 不绕过致命错误或未知碰撞 |
| 单次提交 | 请求参数、时间、回调结果、新实体 | 超时/失败先核实是否部分生效 |
| 读回 | 新 ID、双向通行、站点关系、装载配置或车辆分配 | 标为待核对，不重复施工 |
| 验收 | 静态结果、观察的模拟时间/速度、用户反馈、保存状态 | 如实写明尚未验证的部分 |

2026-10-03 船坞实测：`errorState.infos` 可能包含原生阻止施工的“放置在海岸线上”，同时 `critical=false`、`messages={}`。必须读取 infos，不能以 critical/messages 为空就宣布可施工。共用预览已返回 infos 与 placementBlocked；批量船坞检查还包括 warnings、实际水域与碰撞。以当前接口类型为准，本机 makeProposalData 接受 SimpleProposal，网上 Proposal 示例不能直接套用。

`applied=true && verified=false`、`mutationAttempted=true`、`street_stop_needs_reconciliation` 或超时均进入“状态待核对”。这不是可自动重试的失败。即便原生命令设计为整份提交，引擎断言也曾留下替换道路和孤立对象；不能假定失败会完整回滚。

每次操作的记录应有：任务、会话、输入、预览文件、提交次数、修改前后 ID、验证结果、存档名和未解决事项。JSON 结果与存档分别保存，不能只留聊天结论。

## 5. 道路与铁路建设

### 5.1 道路接入

- **道路走向（2026-10-03 用户指定）**：新建道路优先采用直线或平滑曲线，避免不必要的折线、急弯和连续反向弯。延长既有道路时，优先沿末端切线方向直线延伸；需要绕障或调整接入方向时，再用与原路方向连续的平滑曲线过渡，不为连接近处目标突然折转。
- 直线延伸是优先方案，仍须满足地形坡度、碰撞、设施扩建空间和实际接入要求。预览时检查整段走向、接点切线及坡度过渡；受约束无法直延时说明原因，并选择转弯更少、更平顺的可行方案。本规则不自动授权改造既有道路。
- 连接到真实道路节点，而非仅将端点坐标放近旧路。路段中间接入需要受支持的切分方案，不能凭视觉相交认定接通。
- **异常提交后的组件完整性**：BASE_EDGE/BASE_NODE 仍存在、新边未出现，不足以证明回滚成功。必须只读检查目标端点与相邻道路的 TRANSPORT_NETWORK；缺失时停止原生预览和提交，加载施工前备份后重新检查。2026-10-03 曾确认界面选择道路也因缺失组件触发 Engine.h:323。区分原始备份与带 autosave_ 前缀的同名后续自动存档；备份重载后全图组件存在仍不证明长期模拟安全。
- **2026-10-03 三门峡接路修正**：设施 `frozenEdges` 两端中，必须排除 `CONSTRUCTION.frozenNodes` 后才选外部端口；度数为1、距规划入口最近都不能证明是外部端口。产业道路锚点也要检查冻结节点。本次误选货站内部冻结节点87917（外部端口为87918）时，单体道路预览仍通过，但提交触发 `TransportNetworkSystem.cpp:635 / AreAllNodesEmpty`。关闭自动路口刷新后同一内部节点仍触发断言，故不能将自动刷新认定为根因。当前接口在预览和提交前拦截显式冻结节点，自动吸附排除冻结节点。此编号只作事故说明，不得复用。
- 该图修正后曾采用“新增道路 → 独立路径检查 → 保留原转向、横道和信号的受限路口配置补齐 → 再次双向检查”；不通过替换路段强制刷新。回档前27条连接通过局部检查，但当时其他位置存在缺失组件，不能据此认定整个存档安全；恢复原始备份后这27条道路未保留。现场和修订脚本见 `exports/newmap_plan_20261003/construction/`，历史失败请求仍保留，不自动重发。
- 保留原道路车道、样式、切线和端点配置。替换旧边时，同步更新车道连接及人行横道引用。
- 施工完成后检查每个接入点 **CAR/TRUCK 双向寻路**，路径必须经过原路 → 接入节点 → 新路。能从其他路绕行到终点不算该路口接通。
- 当前 bridge 的道路收尾逻辑会处理原尽头空配置及必要刷新；不要绕过它另行连续执行清空/替换实验。已有非空自定义转向和信号配置必须保留，健康路口不要重建。

## 6. 双侧停靠点：重点防 crash

使用当前 `B.commands.build_street_stop` / MCP `build_street_stop`，先预览、后单次提交。当前版本支持经过检查的施工；历史文档中的“apply 禁用”是旧阶段，不代表现状。

本次确认需要同时满足：

1. 新路段保留原始车道/样式；不要用另一道路模板覆盖。
2. 同一份提案中，把端点配置里的旧路段引用重映射到新边：**车道连接和 crosswalk 都要处理**。漏掉横道引用曾触发原生 map lookup 断言。
3. 双侧停靠对象和新路段 `comp.objects` 引用匹配。已验证实现使用 `-400000000`、`-400000001` 这组原生提案保留 ID；它们不是实际世界实体 ID，也不是可随意生成的编号规则。

- 覆盖使用 `catchmentAreaSystem.getStationCatchables(station,true)` 与需货库存实体求交，多个站取并集去重。直线半径只是候选筛选，不能充当真实覆盖。
- 本次工业区道路停靠点支持 `cargoUnload=true`、`cargoLoad=false`，可复用卸木板；不要默认所有公交站都能装卸货。
- 直升机场（heliport）接通道路后可承担客运和货运，兼有购机维护能力；优先使用自身终端，不默认在旁边另建小型停机坪。原生终端配置已核对 `passengers=true`、`cargo=true`。仍须检查道路/步行接入、实际库存覆盖和装卸；现有旁侧停机坪的线路先迁移验收，再按授权清理。
- 逐一验证来源能装目标货物、目的地能卸货、车型能承运。避免为了货运额外建设已有站点已能完成的设施。
- 原生仓库本身无需道路接入，不为仓库收发货单独修路；货车站仍须有车辆可达的道路。中转要求参与站点覆盖同一仓库库存，不要求站点互相覆盖。城市、工厂不能直接取用仓库内容，仍需车辆配送；乘客的有效通路要求不能套到货运仓储上。规则、官方来源和验收方法见[仓库中转规则](../strategy/TRANSPORT_CARGO_CONNECTIONS.md#仓库无需接路与货物中转规则)。
- TF3 跨运输方式中转须核对共享仓库库存：例如农场货车→公路货站→中转仓→直升机。用 `getStationCatchables(station,true)` 确认货站和停机坪都覆盖同一 `STOCK_LIST`，然后以仓库 `itemsUnloaded/itemsLoaded` 日志、车辆实际载货和城市交付计数验收。`getStation2stationsAndDistancesMap` 在原生 GUI 中用于旅客换乘，不能把它当成货物中转表；两站邻近或没有该表条目都不能独立证明货运是否可用。
- 从远处车库首次出库可能耗时很长。车辆尚未到源站时，用 `MOVE_PATH.dyn.pathPos.edgeIndex` 和路径长度辅助区分行驶中与卡住；路径会重算，不能将分段索引直接换算成全程百分比。持续远离维护范围的集货车应配置合适的本地维护设施，读回 `maintenanceStation` 和维护状态变化。

### 7.2 站点方向与货品配置

枚举可用 station/terminal，使用实际 `vehicleNodeId` 做 BUS/TRUCK 寻路，包含末站返回首站，比较完整回路长度。本站最短不一定全线最短，双侧站的方向必须联合选择。

索引约定：线路的 `station`、`terminal`、cargo ID 是从 0 开始的语义编号；Lua vector 的访问通常从 1 开始。读取 `group.stations[station+1]`、`terminals[terminal+1]`；装载向量用 `cargoId+1`。不把“车站实体 ID”填进 `station` 字段。

`Line.Stop.new()` 的默认装载向量为空，曾导致“该线路未设置装载任何货品”。创建线路必须显式填充，示意如下：

```lua
local config=api.type.Line.StopConfig.new()
local loads,maximum={},{}
for cargoId in pairs(api.res.cargoTypeRep.getAll(true)) do
  loads[cargoId+1]=isSource and cargoId==targetCargoId
  maximum[cargoId+1]=1
end
config.load=loads
config.maxLoad=maximum
config.forceUnload=false
stop.stopConfig=config -- 完成字段后再放入 stops vector
line.customFilters=true
```

公交线每站启用旅客；货运线仅在来源启用目标货物，目的地 `load=false` 是禁止装货，不是禁止正常卸货。不要为了配送强制 `forceUnload=true`。

创建前按名称和站组顺序检查是否已有等价线路。提交一次后比较线路清单，读取实际 stops、完整 load/maxLoad 向量和 `getProblemLines(player)`。无问题列表不能替代配置验证。

当前通用 `create_line` 会初始化货物向量，但默认 station/terminal 为 0，并可能为货站开放多种货物。需要指定方向或单货种时使用经审查的专用构造逻辑。不要假定通用接口已经完成全线路径优化。

## 9. 保存与重载

保存使用 GUI 环境的原生入口。2026-10-05 修订：Agent 正常检查点、完工和运行观察结束存档，同一地图共用 `tf3_fullmap_auto_map_<地图标识>`，覆盖前次，不随规划内容、任务、批次或规划摘要变化。地图标识按完整城市中心坐标集合排序后计算，不包含城市名、生产设施、线路及规划内容，避免改名或勘探产生新槽。完整城市清单缺失时不能猜测槽位；不允许用局部城市清单生成保存身份。相同地图布局的测试副本共用此自动槽，副本切换前的恢复备份必须独立保留。施工前备份和异常现场继续使用阶段、时间及唯一后缀。旧哈希槽不会自动删除；首次采用新规则会创建地图槽，之后复用。游戏自身 `autosave_...` 轮转存档不受此 Agent 规则控制。

```lua
app.saveGame("<固定自动存档名或独立备份名>",function() end,false,true)
return {requested=true}
```

- **不要写 `_G.xxx` 或未声明全局变量作为保存完成标记。** 本次 `tf3StopCheckpointDone` 全局写入曾使 GUI Lua 退出。局部变量与空回调可避免这一具体错误。
- `requested=true` 仅证明调用已发出。覆盖前记录 `.sav` 文件状态，保存后必须确认文件状态已变化、大小非零且连续检查稳定，旧文件未更新时不得报成功。文件更新也不证明能重新加载。
- 重载验证只在用户已授权时执行；没有重载就明确写“未验证重载”。不要自动覆盖已知稳定存档。
- 重载后清理会话缓存、重新枚举所有目标；旧线路/站组 ID 可能指向完全不同的对象。

## 10. 崩溃分类与处置

| 现象 / 证据 | 本次结论 | 下一步 |
|---|---|---|
| 替换路段时原生 map lookup 断言 | 停靠点提案漏映射横道引用是已确认触发点 | 同步保留并映射 lane/crosswalk；先核对部分修改 |
| `CalcNodeIndex`，几何预览成功但应用失败 | 历史停靠提案缺少边对象引用/终端网络 | 使用当前完整接口；查新路及孤立对象，禁止重发 |
| GUI 保存回调写全局时报错退出 | agent 回调脚本错误 | 空回调；核对文件而非写全局标记 |
| `SimEntityUpdateHelper.cpp:384 / MakePersonCapacityData` | **根因未解决**；孤立对象清理不是修复 | 归档最新日志，从已知稳定存档逐阶段对照 |
| “该线路未设置装载任何货品” | 默认装载向量为空，是配置错误 | 显式填满 load/maxLoad；不能称其为已证实 crash 根因 |

历史证据边界：

- 故障存档在移除孤立对象、无车辆版本及用户删除线路后仍报告崩溃，因此不能认定某款公交车或线路存在就是根因。
- `controlled_simulation_trace.json` 记录实际 1 倍速推进到约 24.94 秒后心跳超时，结合当次崩溃调查，不支持“只有 4 倍速才会崩溃”。超时本身仍须与进程/日志核对，不能独立当作 crash 证明。
- 数千个建筑、节点和居民目标静态检查通过仍没有排除模拟期错误。
- 用户恢复已知稳定存档后，六处停靠点重建获得“没有闪退”反馈；随后线路修正装载配置后用户报告正常。两张地图的车库位置、模拟年龄等也不同，不能将差异单独归因于停靠点。
- 木板线和新货车完成路径/配置读回；本次尚未记录该车完整送货周期和购车后的独立保存/重载验证。

发现新崩溃后的顺序：

1. 停止提交写命令；确认游戏进程、心跳和加载状态。不要用重发建造作为连通测试。
2. 从 `D:\Program Files\Steam\userdata\1112836998\3493540\local\crash_dump` 按修改时间找本次日志，复制到独立 `exports/crash_<时间>/`，保留原日志与 dump。不要把历史同名日志当最新日志。
3. 记录断言、时间、最后命令、加载存档、实际速度、车辆/线路状态及部分修改证据。未知项明确标未知。
4. 用户加载后先只读复核，重新定位实体并失效缓存；保存故障现场，不覆盖正常基线。
5. 如需受控复现，从已知稳定基线一次只加一类操作：停靠点 → 无车辆线路 → 单辆车。记录模拟 tick、gameTime、真实速度与观察时长；用户速度变化使定速比较失效。
6. 对同一断言重复失败不继续随机清配置、拆建筑或清理居民；先对照证据。`pcall` 只能捕获 Lua 错误，不能保护 C++ assert 或访问违例。
7. 报告静态验证、模拟观察和根因证明三个不同层级。短时没崩溃只能说“观察期间未复现”，不能说彻底修复。
