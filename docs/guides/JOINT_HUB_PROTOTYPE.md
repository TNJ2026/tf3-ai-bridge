## 2026-10-04 动态入口绑定取得进展

新增 `hub_joint_bind_probe.lua`：在同一个引擎请求中先展开联合预览，从本次生成网络识别客/货站内部连接和唯一外部入口，再移除重复的显式道路端点，将道路改为引用本次生成入口，重新预览。未使用历史负编号常量；歧义、缺失、正数世界节点或重绑后入口丢失会停止。仅当实验 spec 的 `bindGeneratedPorts=true` 时启用；没有施工提交接口。

现场证据：`exports/joint_live_bind_20261004/`。当前镜头约 `(5766.25,-1138.63)`，重绑后原生预览只报告既有世界实体碰撞，之前的负编号组内碰撞消失。对返回网络按完整 `(entity,index)` 和 BUS/TRUCK 模式做有向遍历，客站与货站到新道路均可出站、返站；结果在 `vehicle_paths.json`。该检查不等于所有站台、所有路口或步行换乘全部通过。

当前显示区域仍有仓库、停机坪和车站，不能在这里提交重叠的新集合。已保留原生备份 `tf3_joint_before_20261004_082215.sav`，没有实际建造。本例证明动态入口重绑能消除这类组内重复节点问题；尚需在无外部碰撞位置完成整体验证、一次提交、独立读回和存档验证。原生重建提案的部分运行时字段与本机类型定义有差异，不能仅凭文档声明当作已读取的数据。

## 已确认的接口能力

依据本机 TF3 官方 API 定义（`E:/SteamLibrary/steamapps/common/Transport Fever 3/api/tealdef/`）：

- `api/type.d.tl:2808` 附近的 `SimpleProposal` 同时包含 `constructionsToAdd` 和 `streetProposal`，并规定新实体使用负编号。
- `api/cmd.d.tl:961` 的 `makeWorldBuildProposalCmd` 接受 `Proposal` 或 `SimpleProposal`。因此同一提交携带四座建筑及道路在接口结构上可表达，不是只能顺序调用四次建造。
- `api/type.d.tl:2688` 的 `ProposalData` 提供 `entity2tn` 和 `tpNetLinkProposal`，可供联合预览后检查生成的网络。
- `SimpleProposal.ConstructionEntity` 没有显式的“将生成的入口绑定到指定新道路节点”字段。负编号不能凭源存档实体编号推断；坐标重合也不是连接成功的证据。

## 已准备的测试包

## 未完成的验证与正式启用条件

本轮只检查本地官方定义、生成测试包并运行离线测试，未连接游戏、未执行原生联合预览或提交。该原型不注册成正式建造接口。

独立测试存档中，先选无碰撞空地，明确坐标，再验证四设施与五段组内道路的联合预览。检查生成入口是否与预定道路节点实际连通，并检查 CAR、BUS、TRUCK、PERSON 各自需要的路径。明确的预览拒绝应保留诊断；断言或超时不得重发。若入口未合并，需继续查原生吸附/提案展开机制，不用重复道路或 `ignoreErrors` 强行提交。

只有联合网络绑定得到证实后，才能增加单次提交和独立读回步骤；还须验证仓库覆盖、模块保留、存档重载与模拟，不将预览通过称为完全实现。外部公路接入仍需目标位置设计；本包只测试集合内道路。
