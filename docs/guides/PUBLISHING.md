# 模组发布流程

## 操作前必读

涉及模组信息更新、发布副本同步、清理、打包建议、校验或上传时，先完整阅读本文，再读取相关脚本及连接文档。不能仅凭打包脚本的存在推定发布方式。本文是发布流程的统一入口；连接文档及历史打包记录不替代此流程。

默认通过游戏 **Mod Hub → My Mods** 校验并上传，不生成 ZIP。只有用户明确要求 ZIP 时才使用 `scripts/build_mod_package.py`。仅要求更新文档或检查问题，不代表授权上传、重载游戏或恢复监控。

## 本地发布配置与 Git

实际 `mod/tf3_mcp_bridge/mod.json`、`_metadata/modinfo.json` 和 `_metadata/mod.io*` 发布绑定文件仅保留在本机，不提交 Git。作者、发布说明和个人发布信息写入这些本地文件；仓库仅保留 `mod.example.json` 与 `_metadata/modinfo.example.json` 示例。示例中的技术 `modId` 是脚本资源命名空间，不能单独改名。

首次检出仓库时，将两个示例分别复制为同目录的 `mod.json` 与 `modinfo.json`，仅在目标不存在时创建，再填写本地作者、版本及发布说明。不要用示例覆盖现有个人配置。发布和测试仍读取实际本地文件，发布前按下文校验。

更新模组信息时同步本地源码配置和游戏发布副本即可，不再将个人配置纳入 Git 提交。`.gitignore` 不会清除已提交或已推送的历史；如需清理历史，须单独确定范围后执行。

## 版本同步规则

每次模组升级必须同时更新以下字段，不得只更新其中一项：

- `mod/tf3_mcp_bridge/mod.json` 的 `revision`：整数修订号，每次升级递增。
- `content/tf3_mcp_bridge/bridge.script.lua` 的 `BRIDGE_VERSION`：桥接版本字符串，每次升级提高版本号。
- `_metadata/modinfo.json` 的介绍版本文字和更新说明标题：使用本次桥接版本号，与 `BRIDGE_VERSION` 完全一致。

修订号和桥接版本号同时更新，但不要求数值相同。发布前读取源码、本地发布副本以及上一版实际发布记录，按实际上一版确定递增值；不把文档中的旧示例当作当前版本，也不把尚未上传的工作区版本当作已发布版本。

源码与游戏本地 `staging_area/tnj_tf3_ai_bridge/` 发布副本必须同步上述字段。更新说明按桥接版本号组织，例如 `更新内容 / Changelog — v0.12.21`，不以日期作版本标题。保留中英文说明，简洁描述修复的问题或新增功能，不在模组介绍中展开实现细节或列出未验证问题；验证证据和限制另记开发文档。

## 游戏内上传

按当前用户要求，从游戏的 **Mod Hub → My Mods** 校验并上传本地发布副本，不生成 ZIP，不以 ZIP 上传作为默认流程。除非用户另有要求，不调用生成 ZIP 的 `scripts/build_mod_package.py`。

发布前核对：

1. 源码与本地发布副本的修订号、桥接版本、介绍版本及更新标题一致，且相对上一版同时递增。
2. 本地发布副本中的正式 userdata 接收器保持启用；开发源码仍可能保留供诊断工具配置的关闭初始值，不直接用整份开发脚本覆盖已启用的接收器。同步功能代码时保留或显式配置发布接收器设置。
3. 发布副本不包含测试探针、请求文件、存档、日志或个人 MCP 配置；按下节检查 `content/tf3_mcp_bridge/no_gui/`，不能只删除独立测试脚本。
4. 对本地发布目录运行 `scripts/check_mod_package.py "<本地发布目录>" --require-receiver`，代码有修改时完成相应编译及功能检查，再进行游戏原生校验。
5. 上传完成后记录实际上传的修订号和桥接版本。仅修改本地文件不报告为已经发布。

旧发布产物、账本及验证记录保留历史版本信息，不为了统一当前版本而改写历史证据。

## 运行时残留清理

`content/tf3_mcp_bridge/no_gui/` 是 demand / indexed 模式的运行时请求资源目录，不属于发布内容。删除 `ingress_probe.lua` 等测试脚本不会清除该目录。发布副本应与日常运行目录分开，避免再次生成请求文件；不要直接打包运行中的模组目录。

1. 确认实际校验的发布根目录及 MCP 配置指向的目录，核对接收器模式、代次、活动写入和 pending。接收器离线不等于没有未知请求；不能凭文件较旧就认定可删除。
2. 若目录仍被活动会话使用，先停止相关写入并核对原请求；结果未知时保留证据，不清 pending、不重发请求。可另准备不含运行时文件的发布副本，避免修改活动通信目录。
3. 对确认可移出的残留，解析并核对绝对路径，确认目标位于指定模组根目录内且没有意外符号链接或目录联接。将整个 `no_gui` 目录移至模组目录之外的备份位置，记录来源、备份路径及文件数量，独立读回确认。不要仅将文件名转为小写，也不要将备份留在发布副本内。
4. 不清理外部 `tf3_mcp` 请求账本、锁或 `mod_presets` 邮箱；这些不是发布目录清理对象。检查其余测试探针、存档、日志和本机配置是否混入发布副本。
5. 清理后执行带 `--require-receiver` 的离线检查，再从游戏内重新校验。普通目录检查通过只证明文件检查通过，不代表正式接收器配置正确或游戏原生校验通过。

## 校验结果判读

读取游戏生成的 `local/mod_validation_result.json` 时，先汇总 `criticalPc`、`criticalConsole`、等级、消息类型及路径，不逐条输出大量重复消息。确认报告修改时间及 `modId` 属于本次校验。

- `File path contains uppercase characters` 是文件名大小写警告；若路径均位于 `content/tf3_mcp_bridge/no_gui/`，说明发布副本混入了运行时请求文件，应按上节移出，不能通过批量改名掩盖问题。
- 2026-10-16 的现场报告包含 2067 条此类警告，无致命错误；移出目录共 2107 个文件，说明警告条数不等于残留文件总数。该记录仅是历史样例，不能代替当前校验。
- 清理文件不会改写旧校验报告，必须重新运行游戏原生校验并读取新结果。分别报告“目录检查通过”“原生校验通过”和“上传成功”，不得混为完成发布。
