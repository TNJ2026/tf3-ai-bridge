# 全图规划准备与耗时优化

2026-10-05 用户修订：取消独立的双停机坪生产集合类型。城市与陆上生产点统一采用完整城市集合：直升机场（使用自身两个降落平台）、仓库、货车站、客车站、公路车库及组内道路。优先复用，不按城市或工厂数量固定新建；捕鱼港口六设施集合保持不变。当前地图及已有设施、线路不改动，此次仅更新文档。

实现边界：本次未修改配置 JSON 或规划、施工脚本。现有 `production.json`、生产角色校验和线路端点仍为旧双坪实现，不能把本次文档更新视为流水线已支持统一模板；后续新规划须先完成相应适配并验证，禁止直接执行旧生产模板或仅用城市模板路径替换后盲目施工。

数量规则以[集合数量与共用规则](GROUPED_CONSTRUCTION_WORKFLOW.md#数量与近邻渔场共用规则)为准：城市与陆上生产点不按对象数固定配套；捕鱼港口每个渔场最多一个，两个渔场中心距离不超过 3000 米可评估共用。布局草稿仍先生成候选；最终网络按实际中转需求过滤未用陆上集合，并按距离、水路初筛及可选吞吐预算为近邻渔场共用完整港口集合。最终数量、服务归属和无分配运量对象见 COLLECTIONS.md 与 collection_quantity_decisions；候选数量不是施工数量。现有集合复用与合计吞吐须实时核验，原生预览前不得施工。

新地图候选生成入口为 `scripts/plan_pipeline.py`：输入快照、需求明细、产能，以及仓库内默认模板（可显式覆盖），一次完成模板布局、供给网络、执行清单、统一预检和分类索引。已有完整方案继续使用 `scripts/fullmap_workflow.py` 预检。两者全程离线，不连接游戏，不显示卡片，不以旧地图目录或历史编号代替当前输入。

## 显式模板输入

旧实现（待适配统一城市集合）：`plan_pipeline.py` 默认读取仓库内 `config/planning_templates/city.json` 和 `production.json`，包含设施模块、完整内部接路和独立端口映射。可用 `--city-template`、`--production-template` 显式覆盖。单独使用 `plan_template_map.py` 仍须显式传入这两个模板；不再隐式读取本机 `exports/hub_template_default.json` 等注册表。旧注册表只有 `template` 路径时，应传该路径所指的实际模板文件。模板可以保存在仓库外；相对路径按调用时的工作目录解析。

模板顶层须包含 `facilities` 和非空 `roads`。统一规划规则要求城市与陆上生产点均采用城市五设施角色；现有校验实现中，城市设施角色为 `heliport/warehouse/truck/bus/road_depot`；旧生产分支仍为 `helipad/helipad2/warehouse/truck`，每种角色恰好一项。设施包含 `role`、`resource`、`localPosition:{x,y}`、`relativeRotation`（度）和原生 `params`；道路包含局部 `position0/position1:{x,y}`、模板内节点标识 `node0/node1` 和 `roadTemplate`。从已有集合整理模板时，位置应换算到同一局部原点，保留实际资源和模块参数；可附 `rolePortNodes` 描述共享入口。节点标识只描述模板拓扑，不能直接作为当前地图的实体编号。

流水线会去除旧原生预览证据、校验角色并应用模板适配，将实际使用的模板保存到输出目录 `templates/city.json` 和 `templates/production.json`，供布局子进程读取。模板内容参与缓存键；复用基线时模板内容仍参与校验，可使用默认模板或显式传上次输出的这两份文件。模板缺失或不完整会报错，不会自动读取历史导出文件或连接游戏补齐。

设施可配置 `upgradeReserveM:{minX,maxX,minY,maxY}`，数值为建筑自身局部坐标各侧额外预留的米数，必须有限且非负；省略方向为 0。该范围随设施朝向旋转，参与选址地形、障碍避让、集合间避让、后续设施规划及最终预检。输出 `footprint` 与 `reserved` 均按“平移但未旋转的局部矩形”保存，下游只旋转一次；不能直接拿原始 `reserved` 当作世界坐标轴包围框。默认城市模板的定向预留及估算边界见[城市集合说明](CITY_HUB_DEPOT_TEMPLATE.md#当前规划入口与预留修复)。

旧实现中的城市和双坪生产模板均带 `placementMode: road-first`。城市先建五段主路，再建五设施与三段入口短路；生产端先建四段主路，再建四设施与一段入口短路。施工入口默认 `--mode auto` 按方案内模板选模式，账本及读回证据按集合编号隔离。模板修订使旧选址缓存失效。城市步行验收使用引擎车站间可达表；生产端检查两个坪和货站共同覆盖仓库及货车双向通路。详见[城市集合](CITY_HUB_DEPOT_TEMPLATE.md)及[生产集合使用方法](PRODUCTION_HELIPAD_TEMPLATE.md#使用方法)。

## 先获取平整区域，再选择集合（2026-10-04）

1. `capture_planning_snapshot` 默认在同一次地图读取之后、本地分析采样地形，返回 `flat_areas_path`、区域摘要和精查提示；不增加游戏查询，不显示中间卡片。可用 `include_flat_areas=false` 关闭派生分析。全图粗采样间距按地图大小和10万个点上限选择，通常100～250米；粗采样只用于找到方向。
2. 离线流水线先运行 `plan_flat_areas.py`，输出 `flat_areas.json` 与透明的 `flat_areas.svg` 图层，再生成集合布局。区域按干燥、平缓网格单元四邻接合并，保存精确的逐行单元范围；区域包围框内可能有水域或陡坡孔洞，不能把整个框当成可建空地。此阶段不排除建筑，也不证明覆盖或接路。
3. 集合候选仍在原有有界道路锚点、朝向和外接长度内生成，但先比较**整组旋转占地、组内道路及估算扩建范围**的地形，再核对障碍、城市退距、道路连通分量及接路。先选整组和接路都平缓的候选，然后按最大采样地表坡度、高差和距离排序，避免遇到第一个可放建筑的位置就定址。
4. 默认5%地表坡度、集合5米采样高差仅为规划优先项，20米扩建边带也是估算，均不是原生施工或升级安全阈值。没有平整候选通过全部检查时，保留较缓坡方案并记录 `terrain_screen.fallbackReason`；仍不自动施工。`terrain_screen` 同时保存地形指标、调查范围、采样间距及候选检查数量。
5. 对优选集合和接入走廊补采局部25米地形；更小的端口高差还须原生检查。间距大于25米的方案在 `review_queue.json.localTerrainSurveys` 中列出局部调查范围，`pipeline.json.requiresAttention=true`。此离线入口不自动连接游戏精查，不把插值当新测量。局部新快照需重新做布局检查，实际固定道路端口必须重新解析和预览。

`flat_areas.json` 保存地形网格摘要和策略版本；布局缓存包含地形策略，流水线缓存还包括分析代码。换地形或算法后不复用旧选址。单独执行 `plan_template_map.py` 时也先生成或核对平整区域文件；旧文件与当前网格不一致则拒绝使用。

城市与陆上生产点中心距离小于 3000 米时，先按[共用集合规则](GROUPED_CONSTRUCTION_WORKFLOW.md#无限资金模式的默认集合选址)评估共享：城市定址 → 道路效率筛选 → `shared_industry_hubs` 映射 → 未共用生产点定址。网络生成解析映射，合并同向货流并避免同集合航空自环；共用容量和工厂真实道路出入口仍需验收。缓存包含共用规则版本；既有施工方案、建筑和日志不自动迁移或拆除。

## 找不到天然平地时的地形平整

城市候选不再把距离仅作为地形相同时的最后排序项：先遵守退距、通达、碰撞等硬约束，再按服务道路距离与地形共同排序，避免为很小的平整度收益绕远。最终数量确定后，执行[城市集合之间的统筹选址](GROUPED_CONSTRUCTION_WORKFLOW.md#城市集合之间的统筹选址)，读取 `CITY_SITING_REVIEW.md` 和 `city_siting_reviews`；相邻或潜在重复服务的候选未完成共用、分建、换址比较前，不得批量施工。比较须包含实际公路配送、合计吞吐、噪声污染、城市扩张、升级空间及近处有限平整方案。此规则不会自动修改已建地图。

2026-10-04 用户允许：天然平地不能满足集合布局及接路时，可使用地形平整工具。选址顺序为“天然平地 → 调整位置、朝向或布局 → 有限范围平整方案”。地形平整不能解决碰撞、退距不足、货物覆盖不足或道路不通，不能因工具可用而略过这些检查。

规划交付应为需要平整的集合记录：天然平地候选被排除的原因、集合及升级用地、拟平整边界与过渡带、目标高程及估算挖填高差、既有道路接入高程、外接道路坡度方案、受影响对象、局部精查范围及尚未解决的问题。局部精查范围须覆盖外接道路全程和边缘过渡，不能只调查集合建筑。未知高程或微地形标为待精查，不自行补成可施工结论。

只规划任务到此为止；已有集合建造授权时，必要平整可以作为前置工序执行。执行顺序为：确认当前 TF3 工具能力和实际影响范围 → 保存施工前存档 → 平整并读回 → 重采局部地形和实体 → 重新设计及联合预览集合与道路 → 按依赖施工。平整属于世界修改，会使受影响范围的地形分析、候选及预览失效。

0.12.9 已接入[矩形地形平整接口](../reference/TERRAIN_FLATTEN.md)，但全图离线流水线不会自动调用施工工具。需要平整的方案仍保留前置工序待处理状态。接口只支持矩形统一高程、16米保护带检查和边缘坡度限制，支持可选平滑过渡（transition_width），最多256个原生步骤，异常停批；原生地形 Proposal 预览绑定不可用，返回结构检查结果。不得以降低筛选门槛、修改快照高度或套用其他游戏接口来假装完成平整。

## 2026-10-04：避免边规划边拼脚本

1. 在首次游戏调查前启动 `planning_clock.py start`，完成最终交付后 `finish`。阶段脚本耗时自动写入 `pipeline.json`，与整轮墙钟分开统计。勘探期间继续设计时，不开启排除计时；只有完全停工等待勘探时才使用 `wait-start/wait-end`。
2. 首次生成前校验快照、需求、产能的产业编号/类型/位置，以及模板角色。生产模板缺少第二坪立即报错。对捕获的城市车库/货站共享入口模板，自动应用已验证的20m后退方案并生成短接路；不修改原始捕获模板，不把这一修正当作新地形的原生验收。
3. 陆上生产端只在生产设施所属道路连通分量中找锚点，排除冻结节点；有限候选仍找不到就报告局部设计问题，不能跳到另一片路网。捕鱼港口按[六设施航空集合](GROUPED_CONSTRUCTION_WORKFLOW.md#捕鱼港口集合的固定配置)单独规划，默认包含船坞和船只维护设施；评估复用已建船坞时仍须核对购船角色和双向航路，不以维护范围代替航路。
4. 先检查代表性城市/生产集合与岸线，再批量展开；联合建筑预览失败后，才对该集合逐建筑诊断。不要全图重复跑单体预览，最后才发现入口冲突。`review_queue.json` 保存检查顺序、对象和最多三个候选的预算，只是队列，不自动执行原生调用或放行施工。
5. `--baseline` 复用离线布局/网络；缓存同时校验输入、模板、算法代码及输出摘要。产能变化只重算网络，几何/快照变化使布局缓存失效。`--redesign <owner实体编号>` 在同一输入下只重选指定集合，供给网络及全图空间/依赖预检仍重算。复用时清除原生结果和令牌。
6. 局部原生检查用 `plan_native_preview.py --owners T<城市ID>,I<产业ID>` 或 `--ids <规划对象ID>`。集合相关设施、接路及城市停靠点可分别按 section 批量检查；未知编号立即失败。范围筛选不证明其他对象仍然有效，正式提交前仍须重新读取当前世界。
7. 直接交付流水线生成的分类索引；只有必要的复杂岸线、原生失败或供需解释另补专题，避免重复手写整套报表。`plan_refine_sites.py`、`plan_finish_delivery.py` 含怀化专用修正，不能作为新地图通用入口。`plan_report.py` 已作为流水线末阶段，直接生成当前地图的 DELIVERY/CITIES/SUPPLY/EXECUTION、设施/线路 CSV 和 report_plan.json；`plan_write_report.py` 仅为其兼容入口，不再输出旧图数据。报告不推断已勘探或原生预览通过。

```powershell
# 开始整轮计时，不连接游戏
server/.venv/Scripts/python.exe scripts/planning_clock.py start --file <本次计时.json>
# 先取得当前地图的三份输入；输出目录必须为空
server/.venv/Scripts/python.exe scripts/plan_pipeline.py --snapshot <当前快照.json> --details <需求明细.json> --capacity <产能.json> --city-template <城市模板.json> --production-template <生产模板.json> --output <新目录>
# 相同几何下，仅重选指定产业集合；更换输出目录保留历史证据
server/.venv/Scripts/python.exe scripts/plan_pipeline.py --snapshot <当前快照.json> --details <需求明细.json> --capacity <产能.json> --city-template <城市模板.json> --production-template <生产模板.json> --output <修订目录> --baseline <上次目录> --redesign <产业ID>
# 需要实时检查时才调用：只读，但会连接游戏；先确认当前会话
server/.venv/Scripts/python.exe scripts/plan_native_preview.py --plan <方案.json> --output <结果.json> --section groups --owners I<产业ID>
server/.venv/Scripts/python.exe scripts/planning_clock.py finish --file <本次计时.json>
```

这些是候选准备时间，不是把36分钟完整规划降到了1秒。新地形的原生岸线校验、真实入口绑定、覆盖和运营检查尚不能省略；本次优化没有连接游戏，也没有新增原生安全证明。离线结果仍可能 `requiresAttention=true`，必须按问题与原生证据逐项处理。

## 固定顺序

1. 采集当前会话的输入，先查看同一快照派生的平整区域，再确定集合候选和局部精查范围；资源勘探完成后重新获取快照。勘探等待单独记录，不计规划耗时。
2. 初选就联合检查设施、升级空间和道路。`search_sites` 可传入 `access.anchor`（当前道路候选锚点）、`access.local_entry`（设施局部入口偏移）和 `access.max_grade`（默认0.10）。按候选朝向旋转入口，在排序前剔除跨水、快照越界和明显陡坡的直连接路。这只是粗筛；弯道、桥梁和真实端口须另行设计，不能把粗筛当原生可建。
3. 新设施编号使用 `fullmap_identity.facility_id(owner, role, context)`，例如同一渔场分别采用 `shore` 和 `air` 上下文。不要自动给重复旧编号加后缀，因为已有引用可能指向另一个对象。执行器在原生查询前拒绝重复编号。
4. 完成初稿后运行统一预检，再处理报告中的问题。编号、引用、任务覆盖、清单姿态/参数、依赖循环在耗时筛选之前校验；旋转后的当前占地及升级预留每轮重新计算，不信任移动前遗留多边形。
5. 原生预览保持每批8项和有限候选预算。局部修改后重跑离线入口，并根据依赖变化及空间冲突复核受影响项目。所有正式提交仍要求新会话核验、实体解析和原生预览；不可复用旧令牌。
6. 一次生成分类汇总、坐标CSV、执行顺序、问题列表和独立阶段计时，最后只导出一次地图卡片。统一报告是预检交付，不自动替代供需分析、设施尺寸依据和完整线路论证。

## 命令

```powershell
server/.venv/Scripts/python.exe scripts/fullmap_workflow.py --plan <方案.json> --snapshot <快照.json> --manifest <执行清单.json> --output <独立输出目录>
# 局部修订后，使用上次输出作为离线缓存基线；输出到新的目录。
server/.venv/Scripts/python.exe scripts/fullmap_workflow.py --plan <修订方案.json> --snapshot <同一快照.json> --manifest <同步修订清单.json> --baseline <上次输出/preflight.json> --output <新输出目录>
```

输入与输出目录必须分离。失败写入 `failure.json` 并返回非零，不继续后续阶段。正常产生 `preflight.json` 也不意味着可直接建造：必须阅读 `requires_attention` 和 `ISSUES.md`。

## 缓存与局部重算边界

- 道路候选缓存只用于同一完整快照摘要、相同算法版本及相同道路参数。换快照、改道路或算法升级即失效。它不缓存实体查询、原生预览或施工结果。
- 道路粗筛只针对快照地形及障碍；规划设施的旋转占地、扩建空间每轮全量复核，不把未变化任务视为空间安全。
- 清单变化通过依赖关系传递到线路、车辆与运行验收；移除项目单独列出。局部重算列表仅用于离线工作调度，不能缩减建造前的当前游戏检查。
- 清单缺少产业指纹时报告阻塞项，不从“城市相同”推断整张地图相同。新清单须在 `session.industries` 中保存资源名和坐标。四处码头若只有位置没有尺寸，同样报告缺少几何，不默认为无冲突。

## 规划前自检与固定交付（2026-10-04 修订）

首次读取游戏前运行 `python scripts/planning_readiness.py`，检查仓库默认模板、节点坐标一致性、端口绑定，以及规划/执行脚本可读、语法和公共道路执行器导入。整个检查不连接游戏。流水线也在布局计算前自动运行该检查，失败写 failure.json，不继续耗时阶段。

默认模板源于单图原生建筑及独立道路几何预览；不携带任何新图施工许可、源实体 ID 或预览令牌。真实端口、库存覆盖、自动步行连接仍按目标地图验收。使用新的模板模块或游戏版本时仍需原生检查。

岸线优先列入代表性检查：码头、船坞与船只维护设施一起调查局部5米地形/水域，每轮保留最多3个有依据候选。码头按原生水侧、陆侧采样点与实际旋转判断；船坞核对完整占地、地表对齐和双向航路；维护设施的水路障碍矩形不是全部浸水的选址要求。陆侧仓库与两个直升机坪同步选址，建后原生核验三站共同覆盖同一库存。岸线筛选以当前实现和原生预览为准，不将一个地图的坐标当通用模板。粗采样通过不取消这一检查。

通用报表使用当前方案而非手写统计；局部修订后可单独重跑 `python scripts/plan_report.py --output <方案目录>`，不重做布局、不连接游戏、不显示卡片。最终仍只调用一次 export_planning_report。

## 固定集合占地加速（2026-10-04）

现有城市和旧双坪生产分支使用 `fixed-footprint-lazy-v1`：按模板几何预计算八种朝向的建筑占地、升级预留、道路边界与整组调查范围。同一进程按几何内容缓存最多 32 份，多个城市或生产点复用旋转结果；位置、朝向、显式占地、预留或道路几何变化自动使用新缓存键。缓存不保存地图实体、原生预览或建造授权，也不缓存模块参数。

选址先平移整组边界、查询当前快照的地形并排序，只对依次进入详细检查的候选展开逐座建筑坐标。保持原有八种朝向、节点数和距离范围，不因速度优化截断候选或跳过退距、障碍、道路通达及覆盖检查。按排名查到首个满足全部条件的位置即停止；无法通过则继续后续候选。沿用流水线的快照/模板失效规则及 `--redesign` 局部修订入口；本次未实现跨快照的局部地形缓存。

`layout_timing.json` 新增 `geometryCache` 与 `geometryExpanded`，各集合 `terrain_screen` 记录展开数和策略。缓存命中也必须在新址做原生预览和读回验收。捕鱼港口仍走独立岸线流程。

离线合成平地对比（150 个锚点）：城市 3600 个候选约 0.323→0.074 秒，生产 7200 个候选约 0.589→0.135 秒，排序相同；约 4.3 倍仅指这次候选筛选阶段，不代表整轮规划或游戏预览提速。证据在 `exports/siting_optimization/benchmark.json`。
