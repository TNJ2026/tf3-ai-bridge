# 有边界的自动恢复（2026-10-12）

本版实现进程外恢复控制器、独立检查点、持久操作账本、单执行者锁、故障分类、一次启动和恢复后原生读回。默认关闭，不启动定时任务，不接管现有施工，不改变游戏速度。用户停止的监控保持停止。

**实现与实机验收分开：当前只有离线故障注入和回归验收；没有在正式存档制造崩溃，没有安装/验证 TF3 自动启动载入器。不能宣称已经实现任意崩溃无人干预恢复。**

## 入口

- `server/src/tf3_mcp/recovery_runtime.py`：恢复状态机和施工接入 API。
- `server/src/tf3_mcp/recovery_adapter.py`：当前 no_gui 通道的查询、保存、进程身份和显式启动入口。
- MCP `recovery_control`：`status`、`checkpoint`、`recover_once`。MCP 服务需刷新后才有新工具。
- `scripts/recovery_control.py`：相同逻辑的一次性 CLI。不是后台服务。

仅本地查看状态，不连接游戏：

```powershell
server/.venv/Scripts/python.exe scripts/recovery_control.py status --directory output/city_recovery
```

配置模板见 `config/recovery.example.json`。模板故意不填历史实体 ID、启动参数、执行文件散列；须根据当前地图填写。MCP 用 `TF3_RECOVERY_CONFIG` 指向配置的绝对路径，`stateDirectory` 也是绝对路径。CLI 的 `--directory` 为同一持久目录；实时动作另外要求 `--config`、`--bridge-dir` 和 `--mod-content`。状态目录必须与地图/任务对应，不能更换目录绕过未决请求或重启次数。

`audit` 是 1～64 个有界原生查询，每项包括唯一 `name`、允许的 `command`、`arguments`、非空 `fields`。字段使用点分路径，仅保存与恢复相关的稳定字段。覆盖当前工程影响的设施/线路配置、库存和账户；字段缺失即停，不作为空值或正常。禁止把 `eval`、建造、购车等写命令放入审计列表。配置中检查点对象 ID 只用于重载同一存档后的独立比对；恢复后的新施工仍须重新调查、获取新实体和新预览。

## 检查点与操作账本

1. 当前游戏必须已经暂停，no_gui 接收器新鲜，主机和引擎均无 pending。
2. 读取完整城市身份、player、gameTime、会话、加载代次/能力版本和配置的对象审计。
3. 先持久化保存意图，再保存到独立 `tf3_recovery_before_<uuid>` 槽，禁止覆盖已有文件。
4. 复用 no_gui 保存的“原生回执＋新文件非空且写入稳定”验证；另保存 SHA-256，并在保存后重新读取原生基线。
5. `RecoveryRuntime.execute(id, plan, prepare, submit, verify)` 用于接入获授权的施工流程。`prepare` 必须只读并获取新鲜原生预览；`submit` 恰好调用一次；`verify` 必须独立读回，不得把提交回执包装成验收。
6. 同一 ID 再调用只返回原记录；换 ID 也不能重试被隔离的同一方案。提交、回执或验证中断后保留未知状态，禁止后续修改。

API 为本地可信集成点，不接受来自游戏文本的可执行回调。`execute_vehicle_batch(..., use_recovery=true)` 已显式接入，第一版支持单车购买、分配、停止状态调整，要求先创建检查点，保留原有车辆批次账本并追加最终独立读回；返回恢复操作记录。返坞和出售需要另行完善当前载货/到库验收，不在本次接入范围。默认 `use_recovery=false` 保持旧行为，历史脚本不会自动迁移到新账本；其他施工流程需要显式接入上面的执行包装器。

`workflow_lock` 持有既有 `warehouse_batch.lock`，与公共批量施工串行。仅当前工作流的请求和 `asyncio.to_thread` 调用可在其内部重入；并发子任务被拒绝，普通 `public_lock` 仍不可重入。进程结束由操作系统释放锁，原账本不删除。人工操作或不使用公共锁的旧客户端不能被该锁阻止，提交前仍要重读状态。

## 故障处理与启动边界

| 证据 | 动作 |
|---|---|
| 进程身份未知或读取进程权限不足 | 停止，不猜测、不启动 |
| 游戏进程仍在、接收器不新鲜 | 标为通信不可用；不判定为崩溃、不强杀 |
| 主机/引擎 pending | 保存原记录；不通过重启或清锁绕过 |
| 已绑定的游戏进程确认退出 | 在显式启动/回档授权、有效检查点和损失策略满足后执行一次启动 |
| 同一恢复已记录启动意图、但没有回执 | 只观察结果；控制器重启也不能重新发送 |
| 启动等待超过期限或原生比对失败 | 停止并保留证据；不自动换备份、不扩大重试次数 |

启动前复制原日志尾部、no_gui 请求账本尾部及进程绑定到事件目录，每文件最多 2 MiB，记录偏移/截断和散列。原账本、请求 ID、错误和存档均保留；日志缺失不能证明没有修改。

目前项目没有经过验证的通用 TF3 命令行载入参数。因此 `bootstrap` 必须由部署者先在独立存档验证：`argv[0]` 是绝对可执行路径，后续参数必须有独立的 `{checkpoint}` 占位参数，运行时替换为指定备份文件的绝对路径；配置 `executableSha256` 和 `validated: true`。可以是经过验证的专用启动器，不能把 `validated` 当作实机验证的替代。控制器使用参数数组和 `shell=False`，隐藏启动器窗口，不调用强制结束进程。脚本/外部依赖还须由部署者固定版本；本层只校验启动器可执行文件。

启动器必须加载指定备份并保持暂停，且加载相同桥接代次。仅启动到主菜单不会通过验收。缺少启动器时预检停止，不能自动退回旧文件桥接或猜 `--load` 等参数。

回档损失也需要证据：可在状态目录提供 `exit_evidence.json`，包含与 `process_binding.json` 相同的 `process`、`session`，`source: native_final_game_time`、不早于绑定的 `capturedAt` 和真实最终 `gameTime`。这必须来自独立原生采集，不能把旧暂停样本改名成最终时间。没有可靠最终时间时默认停止。用户另行明确允许丢弃检查点之后未知量的进度，才可传 `allow_unknown_loss=true` / `--allow-unknown-loss`，记录中的损失仍为未知，绝不冒报零损失。

`allow_launch` 和 `allow_unknown_loss` 是不同的授权。默认每个持久账本最多启动一次，显式策略最多三次；新事件 ID 不重置计数。任意失败事件阻止新事件绕过。配置、代码版本、地图或会话变化不能沿用旧执行计划。

## 恢复后的验收与续作

既有调度器每次只调用 `recover_once` 一步，不开启另一后台服务，不补跑积压。首次恢复调用带启动授权；后续调用只读观察。控制器不自行等待长时间，也不修改定时配置。

启动后至少进行两轮、相隔至少一秒的原生审计：新会话、相同加载代次和能力、相同完整地图身份/player/gameTime、暂停、无 pending，以及检查点对象审计全部相符。备份散列在加载前后均复核。通过后只标 `recovered_paused` / `readyToReplan`；`operationalVerified` 仍为 false，不恢复高速或监控。

所有历史操作转为 `requires_reconciliation`，保留原回执、原会话和原状态。用 `reconcile(operation_id, inspect)` 在当前地图只读调查，返回 `applied` 或 `absent` 及证据；分别记录 `verified_after_recovery` 或 `rolled_back`。未知结果继续阻断。旧操作不会被重发，可疑方案继续隔离。完成对账后才可创建新检查点、重新规划下一步。原生 host/engine pending 的正式对账仍走原有已审计入口；这个账本不代替原生对账。

本版本不自动修复闭源引擎、不自动探索未知接口、不自动改变地形、不随机拆除排错。下一阶段的实机验收应在单独测试存档验证进程退出、指定备份载入、状态比对、未知请求保留和一个新方案的实际运营。正式存档不用于故障注入。
