## 结论

从原生提案结构看，有条件实现“一次提交多个建筑及组内道路”；当前工程尚未实现港口版本。可以先做一次操作驱动的分阶段施工，但必须准确区别单次原生提交与脚本依次提交。

城市集合已有一次提交成功的历史样例，是紧凑四设施及道路；不是所有城市配置的通用保证。该样例客站到机场步行仍未验收，不能声称城市集合已完全验证。

## 能复用和必须改造的部分

- 可复用：局部坐标变换、模块参数保存、唯一提案实体编号、原生错误检查、单次提交日志、备份及读回框架。
- 角色校验：hub_joint_prototype.py 当前只接受城市/生产航空角色，不接受码头、船坞和船舶维护站。
- 高程：现有 point() 按每个设施原点取地面高程，直接套码头会把水上设施按河床放置；必须按角色处理水面高程/原生偏移和陆侧平台。
- 端口：现有重绑器只识别客货站道路入口。货车站绑定可以作为基础；码头水运终端、船坞出口及维护角色不能套用道路节点识别。
- 航路及库存：旧验收器会将未知设施识别为货车站，并固定按航空站检查共同库存。需要港口角色识别、码头—货站共同鱼类库存、船坞到码头/渔场往返路径检查。
- 水陆碰撞：码头单体代码单独区分 WATER_MESH 接触和阻挡；城市联合预览直接拒绝全部碰撞。港口必须移植与实际水运资源一致的判定，不能统一忽略碰撞。
- 原生模块：参考计划使用建造命令参数，部分设施没有展开完整 params；需要规范化为确切原生模块，保留当前码头模块定义，不从模块文件名推断货物能力。

## 地形与布局边界

现有码头与船坞朝向相差240度，反映两处不同岸段；仓库/货站的设计高程又比水侧高约22–30米。它适合作为功能关系参考，不适合原样复制成统一标高的刚性组合。

若需要更紧凑的组合，应重新选较平缓的陆侧平台；可设计有限平整及边坡平滑，并联合核对货车接路高差。不能仅为让布局像矩形而把整片岸线降到水面，不能将陆地平整的验证等同于填海/疏浚验证。

推荐执行顺序：

1. 按目标岸线调整码头、船坞及维护设施各自位置和朝向，确认完整水域占地与陆侧平台。
2. 如果需要且已获施工授权，独立备份并完成地形工程，重新采集地形和实体。
3. 在整理后的地形上生成码头、船坞、维护设施、仓库、货车站及组内道路的联合提案，动态绑定当前货车站入口。
4. 原生预览、碰撞及网络检查通过后，只提交一次；外部公路连接按目标路网单独设计，不复制源节点。
5. 独立验收设施模块、共同库存、道路往返、船舶出库/航路和维护能力；线路/购船另按授权执行。

地形工程与建筑放置暂不承诺同一条原生命令；现有平整是多步骤修改，未知混合提案需独立研究。
