# 载具外观读取与改色

新增 v2 功能：持续线路配色、默认色恢复、逐节颜色/涂装预览提交及本地图片涂装生成，详见[外观 v2](VEHICLE_APPEARANCE_V2.md)。下文保留 v1 实测及边界，新接口尚未实机验证。

新增接口需要接收器 `vehicleAppearanceVersion=1`，桥接源码版本 0.12.23。2026-10-16 已部署并在当前地图完成单辆 Shinjin 微型巴士改色：原生命令读回与独立查询均匹配目标 RGB。尚未验证多辆车辆、整线改色及屏幕渲染效果。

## MCP 工具

- `get_vehicle_appearance(vehicle)`：读取各部件 modelId、RGB、可改色遮罩状态，以及车辆归属和线路。`available=false` 表示未知，`colorable=false` 只有在 `available=true` 时才能解释为确定不支持；整体 `complete=false` 禁止修改。
- `set_vehicle_color(vehicle,r,g,b)`：修改一辆现有车辆的颜色。
- `set_vehicles_color(vehicles,r,g,b)`：依序修改1～64个不重复的车辆ID。
- `set_line_vehicles_color(line,r,g,b)`：取得该线路当前车辆后统一改为指定颜色，最多64辆；不修改线路本身的颜色，不持续追踪新加入车辆。目标列表无法证明完整时拒绝，不截取前64辆冒充整线完成。

RGB 是有限数字，范围0～1。例如红色为 `r=1,g=0,b=0`。这不是贴图上传、车型替换、逐节车厢改色或购车颜色配置。效果受模型的改色遮罩影响，非所有区域都会变色。

## 执行与结果

写入仅使用受保护的 no_gui 通道。原生端在提交前验证车辆存在、归属当前玩家及颜色数据完整、有可改色部件；调用 `api.cmd.makeEntitySetColorCmd` 后读取实际部件颜色及车型身份，验证通过才能解除原生 pending。客户端再发独立查询验收。数据验收不等同于屏幕视觉或存档重载验收。

多车是逐车修改，不是原子事务，也没有混入 `read_batch`。先读取全部目标并确认归属/数据；没有改色遮罩的车辆返回 `skipped_no_color_mask`。开始修改前将原颜色和目标写入本地持久记录，此后每车保存进度和结果。`complete=true` 表示处理结束，仍需检查各项是否为 `verified` 或跳过，不代表所有目标都改变了颜色。

任一调用异常、回执丢失或独立读回不一致时立即停止后续车辆，保留之前成功项和当前车辆，`complete=false,status=stopped_requires_review`，不自动重试或回滚。游戏命令失败/不完整结果保留原生 pending。不要重新提交整个批次来恢复，须先核对原请求及 journal 中的当前车辆。

日志在 `<TF3_MCP_DIR>/vehicle_appearance/<operation_id>.json`，工具返回 `journal` 的绝对路径。原始通信请求仍使用既有 no_gui 持久账本。无后台同步、无自动售车或模型替换。

## 验证

离线覆盖：读取与改色、原生独立读回、归属/遮罩拒绝、RGB边界、旧接收器拒绝、回调失败、回调丢失、读回错误及 pending 阻断、多车部分成功日志、线路选择和不支持车型跳过。六种 Lua 运行时及保留16个局部变量的编译检查通过。

原生依据和未实现功能边界见[可行性调查](VEHICLE_APPEARANCE_RESEARCH.md)。

## 本次实机发现

新购车辆的原色可能返回 `r=g=b=-1`，这是本次读到的默认色状态，不在当前写入接口0～1的输入范围。当前接口没有恢复默认色入口，不能将其钳制为黑色或白色。本轮通过加载购车后、改色前的已验证存档恢复，不宣称已实现默认色重置命令。后续若接入重置，需明确原生语义并单独验收。
