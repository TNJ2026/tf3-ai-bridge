# 全局、局部规划与可视化工具

核心规划接口始于桥接 0.11.0；卡片能力由 MCP Server 提供。规划与建造分离：调查只读游戏；生成方案和报告只读本地快照，既不暂停，也不建造、购车或贷款。原有 `plan_rail_connection` 继续用于真实铁路站端口之间的工程候选。

## Agent 工作顺序

1. 先 `bridge_status` 和 `get_game_state` 确认当前存档；不要沿用上次地图的城镇编号。
2. `capture_planning_snapshot(output_dir, spacing=250)` 调查全图，无需先建车站。返回 `snapshot_path`、当前城镇/产业清单、状态和覆盖说明。全图建议 250～500 米采样；局部改用 25～100 米。
3. 在返回清单中解析重点城市 ID，调用 `plan_global_development(snapshot_path, focus_town, output_dir)`。得到邻城候选、产业距离清单、分期行动及待调查项。近邻按直线距离初筛，不代表有客流或盈利；图中联系线不是施工路线。
4. 根据全局方案确定城区、产业园或站场范围，再调用 `capture_planning_snapshot`，传 `bounds={"min":{"x":0,"y":0},"max":{"x":2000,"y":2000}}` 等当前有效范围。局部调查也保存全图城镇/产业目录，但地形与障碍仅覆盖指定区域。
5. Agent 依据实际需求、配方、设施模块及交通调查提出位置与功能分区，调用 `plan_local_development` 比较并修订选址和走廊；工具负责几何冲突与流量核算，不代替需求调查。用不同参数调用可保存多个方案，不覆盖旧方案。
6. 全局、局部及铁路规划完成后自动生成 HTML、PNG、SVG、JSON，并直接显示 MCP Apps 图片卡片。不要再调用浏览器或 `open_in_codex` 自动打开 HTML。需要重新显示已有方案时调用 `export_planning_report(plan_path, output_dir)`。报告包含地图、阶段验收条件、供给瓶颈、预留区冲突和不确定事项。
7. 用户授权建设后，再刷新实体/端口并走已有道路、铁路、设施的原生预览及单次提交流程。任何规划结果均为 `buildable=null`，没有隐式建设步骤。

现有 `plan_rail_connection` 可传 `output_dir`，默认使用 `TF3_PLANNING_DIR` 或工作目录下 `exports/plans`，自动保存调查、铁路候选并显示卡片。

## MCP Apps 规划卡片

- 全局方案显示全图；局部方案按设施升级预留区和路线范围加边距裁切，即使输入全图快照也显示局部。没有布局对象时显示调查范围。铁路方案显示候选走廊范围。
- 卡片默认适应窗口，支持 25%～500% 缩放、复位、放大后的滚动查看以及 Ctrl＋滚轮缩放。
- “打开 HTML”仅在用户点击后，通过宿主 `ui/open-link` 打开完整报告。不自动导航、弹窗或打开文件。
- 图片通过工具结果 `_meta.planningCard` 内嵌 PNG 传给卡片，不依赖浏览器访问本地图片文件。工具正文保留规划摘要和文件路径，未支持 Apps 的客户端可继续使用文字结果。
- HTML 链接由 MCP Server 提供，只监听 `127.0.0.1`、仅提供随机令牌登记的报告，不暴露目录。链接在当前服务进程存活且报告未被最近 128 份记录淘汰时有效；重启后可用保存的 `plan_path` 再次调用导出工具恢复卡片。宿主若拒绝链接，卡片显示可复制的链接及本地路径。
- 新版 MCP Server 需刷新连接以载入 `ui://tf3/planning-card.html` 资源和工具 UI 元数据。本次卡片修改不需要重载游戏桥接。

实现遵循 [MCP Apps 协议](https://apps.extensions.modelcontextprotocol.io/api/documents/Overview.html)，使用标准工具—资源关联、初始化与工具结果通知。

## 输入、产物与使用时机

| 工具 | 关键输入 | 产物与用途 | 后续限制 |
|---|---|---|---|
| `capture_planning_snapshot` | 输出目录、调查范围、采样间距 | 当前地图的离线快照与覆盖说明 | 有缺失或采样不足时补查，不能推定空地 |
| `plan_global_development` | 全局快照、当前重点城市、邻城数量、可选供给链 | 区域联系、分期建议、全局报告与卡片 | 近邻及距离初筛不证明需求、盈利或施工可行 |
| `plan_local_development` | 快照、当前及升级占地、候选走廊、可选供给链 | 局部冲突、供给核算、局部报告与卡片 | 选址来自 agent 调查，地表走廊还须工程设计 |
| `plan_rail_connection` | 两个当前车站 CONSTRUCTION ID | 真实端口之间的工程候选及卡片 | 原生预览与单次建设另行执行 |
| `export_planning_report` | 已保存的 plan_path、输出目录与图像尺寸 | 重新导出文件、恢复或重新显示卡片 | 不重新调查游戏，旧图不会因此成为当前地图 |

给每个比较方案使用独立输出目录，保留快照和计划 JSON，便于回看证据。报告中的待调查项应回填到[发展方案模板](../strategy/DEVELOPMENT_PLAN_TEMPLATE.md)，而不是仅交付图片。

## 常见情况处理

| 情况 | 处理 |
|---|---|
| 换图后城市编号与名称不符 | 重新采集与定位，不能只替换显示标题 |
| 局部快照拿来做全局方案 | 重新采集全图；局部障碍／地形不足以支撑全图判断 |
| 预留区相互重叠或走廊穿过预留区 | 修订选址或出入口，保留冲突说明；不把预留空间直接让给道路 |
| 没有合适候选、地形缺失或碰撞未知 | 保留限制并补查或换位置，不强行标为可建造 |
| 图片中文字缺失 | 按下文字体配置重新导出，不需要重复读取游戏或重建方案 |
| HTML 链接过期 | 使用已保存 plan_path 重新导出；不自动打开浏览器 |
| 客户端不显示 Apps 卡片 | 保留文字摘要与文件路径，检查客户端 Apps 支持和 MCP 资源加载 |

## 局部布局输入

```json
{
  "sites": [
    {
      "name": "成品仓库",
      "role": "finished_goods_storage",
      "current": {"min":{"x":400,"y":400},"max":{"x":500,"y":500}},
      "reserved": {"min":{"x":400,"y":400},"max":{"x":600,"y":600}},
      "basis": "示例估算；须核对原生模块尺寸、扩建方向与出入口"
    }
  ],
  "corridors": [
    {"name":"配送走廊","mode":"road","start":{"x":100,"y":500},"end":{"x":900,"y":500}}
  ]
}
```

以上坐标只是说明格式，不可直接用于当前存档。`reserved` 必须完整包含 `current`，还应包含升级建筑、出入口与接驳通道。`basis` 必填，用于区分原生尺寸与估算。工具检查既有障碍、拟建设施之间的预留区重叠、地形覆盖、水域采样和高差；不会自动忽略“准备拆掉”的建筑。坐标均为世界米，北向上。

产业园可分别记录原料仓库、加工厂、成品仓库、铁路货站、公路装卸区、车库及维护设施，不应只画一个没有内部功能的园区外框。资源产地与适合集中加工的设施分开规划，最终按城市需求分配货流。未知的后期需求保持待调查状态。

`corridors.mode` 支持 `road`、`rail`。端点应放在建筑和预留区外的接入候选点。搜索避开非道路障碍及升级预留区；既有道路交叉单独列出。输出是地表走廊，折点未做工程曲线设计，`maxGroundGrade` 也不是设计坡度。铁路应继续调用 `plan_rail_connection` 检查真实站端口、曲率、坡度和桥隧。水运不套用陆地寻路，需另查航道与码头端口。

## 供给与仓储核算

全局、局部工具均接受 `supply_chains`：

```json
[{"name":"鱼类供给","cargo":"fish","time_unit":"game_minute","evidence":"forecast",
  "demand":10,"production":20,"transport":15,"handling":12,"delivery":8,
  "batch":100,"delay":2,"storage":100}]
```

这是说明公式的预测数据，不是当前存档数值。前五项为同一时间单位下的有效流量；`batch`、`storage` 为货物数量，`delay` 使用相同时间单位。`evidence` 为 `measured` 或 `forecast`。未知数值不填零，应暂不提供该链并保留调查项。

- 有效交付上限取需求、生产、干线、装卸、末端能力的最小值，显示需求缺口和限制环节。
- 建议缓冲容量采用保守的 `batch + demand × delay`，并列出当前库容缺口。这是规划估算，不能提高持续吞吐，也不代表精确库存峰值。
- 加工链先按配方换算为同一成品的等效流量；共享线路与多城供应须汇总需求和分配能力，不能给每条支链重复分配整条干线的容量。
- 维护损耗、等待、装卸、时效约束须在输入有效能力时计入；工具不从车型标称载量自动推断。

## 数据和验证边界

地图调查在一次引擎命令内读取可用地形和障碍包围盒，保存状态、版本、范围和实体修订信息。地形最多 100000 个采样点；边缘不整除采样间距的窄条可能不在采样网格内，出图以网格实际范围为准。没有包围盒或无法读取的模型不等于空地。调查不是完整存档，也不保证跨读档实体 ID 仍有效。

方案内嵌输入快照与摘要哈希，方便离线复现；文件不是实时缓存。HTML/图片会标注“未通过原生施工校验”。读取当前地图不提供新的建造授权。

Python 增加 Pillow 依赖；标准环境使用 `uv sync --directory server --extra test` 安装。PNG 优先使用 Windows 微软雅黑或 Linux Noto CJK，其他环境可用 `TF3_PLANNING_FONT` 指定字体。找不到中文字体时导出结果返回提示，HTML/SVG 可使用浏览器系统字体。

刷新 MCP Server 以发现四个新工具；游戏端加载包含调查接口的桥接（最低 0.11.0，并与部署代码匹配）后使用调查接口。测试覆盖离线规划、预留冲突、越界、不完整数据、报告转义、PNG/SVG 输出和无站点原生调查；不把这些测试当作施工安全证明。

2026-10-01 验证：完整测试集 146 项通过；当前存档只读调查得到 16 座城市、841 个地形采样点和 6993 个障碍包围盒；通过实际 MCP stdio 调用完成镇江全局方案及 HTML/PNG/SVG/JSON 导出。图片已人工式视觉检查。局部选址与避让使用合成地图测试，不将其示例坐标当作实机建设建议。
